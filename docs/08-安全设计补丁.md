## 1. 背景

05-技术方案文档第 2.2 节定义 Markdown → HTML 管道为：

```
remark-parse → remark-gfm → remark-rehype(allowDangerousHtml) → rehype-highlight → rehype-stringify(allowDangerousHtml)
```

PDF 后端将 HTML 拼入 `<body>` 后交 Puppeteer 渲染。这套链路存在 **3 个安全问题**：

| # | 问题 | 影响面 |
|---|---|---|
| 1 | 前端预览允许 raw HTML 并 `dangerouslySetInnerHTML` | 浏览器 XSS |
| 2 | 后端渲染同样允许 raw HTML | 注入到 Puppeteer 上下文 |
| 3 | Puppeteer 默认执行 JS、加载外部资源、`waitUntil: networkidle0` 会等所有外部请求结束 | 服务器侧 XSS + SSRF |

攻击者只需提交一段 Markdown，就能让后端 Puppeteer 主动向任意外网 URL 发起请求，泄漏内网信息或被用作 SSRF 探测点。

## 2. 修复设计

### 2.1 Markdown 管道：白名单消毒

引入 `rehype-raw` + `rehype-sanitize`，在 hast 树上对所有节点做白名单过滤：

```
remark-parse → remark-gfm
  → remark-rehype(allowDangerousHtml: true)   # 保留 raw HTML 节点
  → rehype-raw                                # 把 raw 字符串转为 hast 节点
  → rehype-sanitize(schema)                   # 白名单过滤
  → rehype-highlight                          # 代码高亮
  → rehype-stringify                          # 无 allowDangerousHtml
```

**白名单 schema** = GitHub 默认 schema + 扩展常用标签：

| 类别 | 内容 |
|---|---|
| GitHub 默认允许 | 段落、标题、列表、表格、`<code>` 类、`<a href>`(http/https)、`<img src>`(http/https) 等 |
| 本项目额外允许 | `<details>` `<summary>` `<sub>` `<sup>` `<kbd>` `<mark>` `<ins>` `<abbr>` |
| 永远禁止 | `<script>` `<iframe>` `<object>` `<embed>` `<style>` 内的脚本、所有 `on*` 事件属性、`javascript:` URL |

### 2.2 PDF 后端：Puppeteer 沙箱

`pdf-generator.ts` 在 `newPage()` 之后立即设置：

1. `setJavaScriptEnabled(false)` — HTML 是静态文档，无需 JS 执行
2. `setRequestInterception(true)` + 请求处理器：仅放行 `data:` URI 和 `about:blank`，其他全部 `req.abort()`
3. `setContent(html, { waitUntil: 'load' })` — 取代 `networkidle0`，因不再发起网络请求

CSS / 字体均**内联**（github-markdown-css、page-break-css、系统字体栈），不依赖外部资源。

### 2.3 取舍：外部图片在 PDF 中不渲染

用户 Markdown 中的 `![logo](https://example.com/logo.png)`，**前端预览可见**（浏览器照常加载），**PDF 输出中为空**（后端拦截）。

**理由**：

- 项目定位"无文件存储 / 隐私优先"，不应让服务器主动外发任何请求
- shields.io / GitHub 头像等"看起来人畜无害"的域，一旦被白名单放行，攻击者可用 DNS rebinding / 重定向链穿透
- README 缺图片不影响主要内容（代码、文字、表格仍完整）

未来若需支持外部图片，应采用**前端预处理上传 → 内联为 data URI** 的方案，而非放行后端外联。

## 3. 验证用例

修复后 `renderMarkdownToHtml` 实测输出：

| 输入 | 输出 |
|---|---|
| `<script>alert(1)</script>` | 空 |
| `<img src=x onerror=alert(1)>` | `<img src="x">`（`onerror` 被剥离） |
| `[link](javascript:alert(1))` | `<p><a>link</a></p>`（`href` 被剥离） |
| `<details><summary>tip</summary>body</details>` | 原样保留 |
| GFM 表格 | 完整 `<table>` |
| 代码高亮 | 带 `hljs language-js` 的 `<pre><code>` |

## 4. 与 05-技术方案文档的差异

| 05 定义 | 08 补丁 | 状态 |
|---|---|---|
| Markdown 管道 5 步 | 7 步（多 rehype-raw + rehype-sanitize） | 替换 |
| `rehype-stringify` 含 `allowDangerousHtml` | 去掉该选项 | 收紧 |
| `page.setContent` `waitUntil: 'networkidle0'` | `waitUntil: 'load'` + 网络拦截 | 替换 |
| 未设置 `setJavaScriptEnabled` | 显式 `false` | 新增 |
| 未拦截外部资源 | 仅 `data:` / `about:blank` 放行 | 新增 |

如 05-技术方案文档与本补丁冲突，**以本补丁为准**。
