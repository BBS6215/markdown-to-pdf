## 1. 背景与决策

### 1.1 触发因素

01–07 文档定义的是一套**前端 (Vercel) + 后端 (Render/Fly Puppeteer) + Supabase** 的三层架构，原始成本估算 $8.67–26.67/月。在 2026-05-13 接近上线时，作者基于以下事实回看了这套架构：

| 输入 | 内容 |
|---|---|
| 历史数据点 1 | WeeklyPlanner 上线至今付费用户 0 |
| 历史数据点 2 | MindTypo 上线至今付费用户 0 |
| 当前认知 | 本项目（MD → PDF/Word/HTML）所属类目（在线小工具）海外付费率历史上同样偏低 |
| 当前阶段 | **流量是否存在尚未验证**，不是付费转化率问题 |

结论：在流量验证之前持续每月 $7–25 的 backend 固定成本是**用现金购买不必要的复杂度**。

### 1.2 决策

**全部转换路径搬到浏览器**：PDF、Word、HTML 三种格式均在用户本地浏览器完成生成，不经过 backend。$0/月运行成本（仅域名年费 ~$20）。等真实流量与付费意愿数据出来之后，再决定是否重启 backend。

### 1.3 与 01-04 文档的关系

01（项目主线）、02（SEO）、03/03-1（产品结构 / 交互）、04（UI 规范）**完全不受影响**。这些是产品定位与用户层文档，技术路径变更不动它们。

## 3. 当前实际架构

### 3.1 整体数据流

```
┌──────────────────────────────────────────────────────────┐
│                    用户浏览器                              │
│                                                          │
│  ┌──────────────┐    ┌──────────────────────────────┐   │
│  │ CodeMirror 6 │───▶│ unified (remark + rehype +   │   │
│  │  编辑器       │    │  rehype-sanitize)            │   │
│  └──────────────┘    └──────────┬───────────────────┘   │
│                                 │                        │
│                  ┌──────────────┼────────────────┐      │
│                  ▼              ▼                ▼      │
│           ┌──────────┐   ┌──────────┐    ┌──────────┐   │
│           │ PDF 路径  │   │ Word 路径 │    │ HTML 路径 │   │
│           │ window   │   │ docx pkg  │    │ Clipboard │   │
│           │ .print() │   │ Packer    │    │  API      │   │
│           │ + iframe │   │ .toBlob() │    │           │   │
│           └─────┬────┘   └─────┬─────┘    └─────┬─────┘   │
│                 │              │                │        │
│                 ▼              ▼                ▼        │
│              用户保存          下载 .docx       已复制     │
│              (Save as PDF)                              │
└─────────────────────────────────┬────────────────────────┘
                                  │
                                  │ (fire-and-forget)
                                  ▼
                       ┌──────────────────┐
                       │ Supabase         │
                       │ - Auth (登录)     │
                       │ - conversion_    │
                       │   history (日志)  │
                       └──────────────────┘
```

**网络出口仅有 Supabase**（Auth 登录、conversion_history 写入）。没有自营 backend HTTP endpoint。

### 3.2 PDF 路径

实现位置：`frontend/lib/converter/pdf-print.ts`

机制：
1. 把 Markdown 经 unified + rehype-sanitize 渲染成 HTML
2. 创建隐藏 `<iframe>` 注入完整 HTML 文档（含 `PRINT_STYLES` 内联样式）
3. 调用 `iframe.contentWindow.print()` 触发浏览器原生打印对话框
4. 用户在打印对话框选择"另存为 PDF"

**优点**：零成本、零依赖、零延迟，浏览器 Chromium 引擎自带的 PDF 渲染质量足以满足海外工具站基础需求。

**已知限制**：
- 无法在代码中检测用户是 Save 还是 Cancel（受浏览器 API 约束）
- 无服务端 PDF 模板能力（页码、页眉、水印等高级特性不可用）
- 代码块当前仅黑灰单色高亮，未实现 hljs 彩色配色（可后续在 `PRINT_STYLES` 中内联 `github-markdown-css` 主题）

### 3.3 Word 路径

实现位置：`frontend/lib/converter/word-export.ts`

机制：
1. 把 Markdown 经 `remark-parse + remark-gfm` 解析为 mdast
2. 自定义遍历器 `convertNode` 把 mdast 节点映射成 `docx` 包的 `Paragraph` / `Table` / `TableRow` 对象
3. `Packer.toBlob(doc)` 输出 `.docx` Blob

样式取自 `D:\GoodApp\ABeiTools_V2` 的 md2word 模块（已为中文场景多轮调试）：
- 基础字体：**微软雅黑**，确保 Word/WPS 上中文不回退到 Calibri
- Heading1-6 字号阶梯：32 / 28 / 26 / 24 / 24 / 24 半磅
- 有序列表渲染为明文 `"1. "` 前缀（不用 docx 的 numbering.config，避免独立列表共享 numbering ref 导致序号跨列表续编）
- 行内样式累积器（`collectInlineRuns → toTextRun`）：保留嵌套 bold / italic / strike / inlineCode / link

### 3.4 HTML 路径

实现位置：`frontend/lib/converter/html-export.ts`（剪贴板）+ `frontend/lib/markdown/render.ts`（渲染）

机制：
1. 把 Markdown 经 unified（含 **rehype-sanitize 防 XSS**）渲染为 HTML 字符串
2. 通过 `navigator.clipboard.writeText()` 直接写入剪贴板

用户用例：粘贴到富文本编辑器（Notion、飞书、邮件正文等）。

## 4. 数据流（Supabase）

### 4.1 Auth

不变：Supabase Auth（邮箱密码 + Google OAuth）。登录后 cookie 由 `@supabase/ssr` 管理。仅用于 Dashboard 历史记录 SELECT 时的 `auth.uid()` 限定。

### 4.2 conversion_history

| 项 | 当前行为 |
|---|---|
| 是否登录用户必写 | 否，匿名用户跳过 |
| 写入方 | **浏览器 Supabase Client**（service_role 已不需要） |
| 写入时机 | 转换成功后，`fire-and-forget` IIFE 包裹，不 await，**不影响下载** |
| RLS 策略 | `WITH CHECK (auth.uid() = user_id)` —— 三种 format 一视同仁 |
| 失败容忍 | Supabase 短暂不可用不影响转换功能本身 |
| PDF 特例 | 由于浏览器 print API 无法区分 Save vs Cancel，**PDF 不写 history**（避免误报） |

### 4.3 daily_usage

表保留（迁移 `20260323100348` 创建），但写入路径已断（无 backend、无配额）。不删除是为了未来重启 backend 时减少迁移成本。

### 4.4 record_conversion RPC

09 号补丁中的 RPC 函数（迁移 `20260513065047`）保留但未调用。同 daily_usage：保留作冷备。

## 5. backend/ 目录处置

### 5.1 当前状态

- 目录完整保留：`backend/src/`、`Dockerfile`、`render.yaml`、Puppeteer 依赖
- 未部署到任何环境（Render / Fly / Docker）
- monorepo 仍把 `backend` 作为 pnpm workspace，但 `pnpm dev` 默认只跑 frontend（见根 `package.json` 的 `dev` 脚本）

### 5.2 未来重启 backend 的触发条件

任意一条达成即可考虑：
- 日活跃用户 > 500 且持续两周
- 出现真实付费意愿（Stripe 测试支付、用户邮件询价等）
- PDF 模板 / 页眉页脚 / 批量转换等高级功能进入产品 roadmap

重启步骤：
1. 在 `frontend/lib/converter/*` 中切回 `POST /api/convert/*` 调用
2. 部署 backend 到 Render Starter 或 Fly.io
3. 重新启用 09 号补丁的 record_conversion RPC + JWT 校验
4. 把 08 号补丁的 Puppeteer sandbox 节恢复为强制要求

## 6. 成本结构

| 项目 | 原计划（05 §1.2） | 当前实际 |
|---|---|---|
| Vercel | $0/月（Free Tier） | $0/月 |
| Render/Fly | $7-25/月 | **$0/月** |
| Supabase | $0/月（Free Tier） | $0/月 |

## 7. 已知限制与后续

### 7.1 已知限制（验收时不修复）

| # | 限制 | 原因 |
|---|---|---|
| 1 | PDF 无法检测 Save vs Cancel | 浏览器 API 限制 |
| 2 | PDF 代码块单色高亮 | 等真实流量验证后再决定要不要内联 hljs CSS |
| 3 | Word 不支持图片嵌入 | mdast `image` 节点当前降级为 alt 文本，需求验证后再加 |
| 4 | 无服务端 PDF 模板 | 等付费意愿验证 |
| 5 | 大文档（>50KB Markdown）依赖客户端 CPU | 浏览器化的固有代价 |

### 7.2 重启 backend 后才考虑的功能

- PDF 模板选择（学术 / 商务 / 极简）
- 页码 / 页眉 / 页脚
- 批量转换（zip 上传 → zip 下载）
- API 售卖（`/api/v1/convert`）
