## 1. 核心数据对象清单

V1.0 涉及 **3 个数据对象**，其中 2 个存于 Supabase PostgreSQL，1 个由 Supabase Auth 托管：

| # | 数据对象 | 存储位置 | 说明 |
|---|---------|---------|------|
| 1 | **用户 (User)** | `auth.users`（Supabase 内置） | Email + Google OAuth 注册用户，无需自建 users 表 |
| 2 | **转换记录 (ConversionHistory)** | `public.conversion_history` | 登录用户的全部转换记录（PDF/Word/HTML），供 Dashboard 展示 |
| 3 | **每日用量 (DailyUsage)** | `public.daily_usage` | 登录用户每日 PDF+Word 转换计数，用于限额检查 |

**不在数据库中的数据对象**：

| 数据对象 | 存储方式 | 说明 |
|---------|---------|------|
| 匿名用户用量 | 客户端 localStorage `md-usage-{YYYY-MM-DD}` + 服务端 express-rate-limit 内存（IP 维度，10 次/天） | 双重检查，不入库 |
| 编辑器内容 | sessionStorage | 跨页面/格式切换保持，关闭标签页即丢弃 |
| 转换生成的文件 | **不存储** | 隐私特性——仅存元数据，文件即时返回客户端后丢弃 |
| 回头用户标记 | localStorage `hasVisited` | 区分首次/非首次访问，影响欢迎文案 |

**设计原则**：V1.0 仅 2 张自建表。不为未来不确定的功能（付费、API Key、模板）预建表结构。

## 2. 数据表设计

### 2.1 表 1：conversion_history

存储登录用户的所有格式转换历史（含 HTML），供 Dashboard 展示最近 50 条。**文件本身不存储**。

```sql
-- =============================================================
-- conversion_history：登录用户转换记录
-- 写入时机：每次转换完成后（含 HTML），由前端 Supabase Client 写入
-- 查询时机：Dashboard 加载时，按 created_at DESC 取最近 50 条
-- =============================================================

CREATE TABLE public.conversion_history (
  id                UUID          PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id           UUID          NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  format            TEXT          NOT NULL CHECK (format IN ('pdf', 'word', 'html')),
  filename          TEXT          NOT NULL,
  file_size_bytes   INTEGER,
  source_size_bytes INTEGER,
  status            TEXT          NOT NULL DEFAULT 'success' CHECK (status IN ('success', 'failed')),
  created_at        TIMESTAMPTZ   NOT NULL DEFAULT now()
);

-- 索引：Dashboard 按时间倒序查询的核心路径
CREATE INDEX idx_history_user_created
  ON public.conversion_history(user_id, created_at DESC);

-- Row Level Security
ALTER TABLE public.conversion_history ENABLE ROW LEVEL SECURITY;

-- 用户只能查看自己的记录
CREATE POLICY "Users can view own history"
  ON public.conversion_history FOR SELECT
  USING (auth.uid() = user_id);

-- 用户只能插入自己的记录
CREATE POLICY "Users can insert own history"
  ON public.conversion_history FOR INSERT
  WITH CHECK (auth.uid() = user_id);

-- 注意：不创建 UPDATE/DELETE 策略——历史记录只增不改不删
```

### 2.2 表 2：daily_usage

追踪登录用户每天的 PDF+Word 转换成功次数。**HTML 不计入配额**（无限制），因此本表只追踪 `pdf_word_count`。

```sql
-- =============================================================
-- daily_usage：登录用户每日 PDF+Word 用量
-- 写入时机：每次 PDF/Word 转换成功后，UPSERT 递增
-- 查询时机：转换前检查 + Dashboard 加载
-- =============================================================

CREATE TABLE public.daily_usage (
  id              UUID          PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id         UUID          NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  usage_date      DATE          NOT NULL DEFAULT CURRENT_DATE,
  pdf_word_count  INTEGER       NOT NULL DEFAULT 0,
  created_at      TIMESTAMPTZ   NOT NULL DEFAULT now(),
  updated_at      TIMESTAMPTZ   NOT NULL DEFAULT now(),

  -- 每用户每天最多一条记录，UPSERT 依赖此约束
  -- PostgreSQL 会为 UNIQUE 约束自动创建索引，无需额外建索引
  UNIQUE(user_id, usage_date)
);

-- Row Level Security
ALTER TABLE public.daily_usage ENABLE ROW LEVEL SECURITY;

-- 用户可查看自己的用量
CREATE POLICY "Users can view own usage"
  ON public.daily_usage FOR SELECT
  USING (auth.uid() = user_id);

-- 用户可插入自己的用量记录（首次使用当天时）
CREATE POLICY "Users can insert own usage"
  ON public.daily_usage FOR INSERT
  WITH CHECK (auth.uid() = user_id);

-- 用户可更新自己的用量记录（递增计数时）
CREATE POLICY "Users can update own usage"
  ON public.daily_usage FOR UPDATE
  USING (auth.uid() = user_id)
  WITH CHECK (auth.uid() = user_id);

-- 注意：不创建 DELETE 策略——防止用户通过删除记录绕过每日限额
```

> **与技术方案文档的差异**：
> 1. 删除了冗余的 `CREATE INDEX idx_usage_user_date`（UNIQUE 约束已自动创建等效索引）
> 2. 将 `FOR ALL` RLS 拆分为 SELECT + INSERT + UPDATE 三条独立策略，不允许 DELETE

### 2.3 触发器：updated_at 自动更新

技术方案文档定义了 `daily_usage.updated_at` 字段，但**遗漏了 UPDATE 触发器**。没有触发器，UPSERT 操作时 `updated_at` 不会自动更新，将永远停留在首次 INSERT 的时间。

```sql
-- =============================================================
-- 触发器：daily_usage 更新时自动刷新 updated_at
-- =============================================================

CREATE OR REPLACE FUNCTION public.handle_updated_at()
RETURNS TRIGGER AS $$
BEGIN
  NEW.updated_at = now();
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER on_daily_usage_updated
  BEFORE UPDATE ON public.daily_usage
  FOR EACH ROW
  EXECUTE FUNCTION public.handle_updated_at();
```

### 2.4 完整执行顺序

在 Supabase SQL Editor 中，按以下顺序执行：

1. 创建 `conversion_history` 表 + 索引 + RLS（2.1 节）
2. 创建 `daily_usage` 表 + RLS（2.2 节）
3. 创建 `handle_updated_at()` 函数 + 触发器（2.3 节）

## 3. 关键字段说明

### 3.1 conversion_history 字段详解

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `id` | UUID | PK, 自动生成 | `gen_random_uuid()`，无需前端传入 |
| `user_id` | UUID | NOT NULL, FK→auth.users, CASCADE | 删除用户时级联删除全部记录 |
| `format` | TEXT | NOT NULL, CHECK IN ('pdf','word','html') | 存语义名而非扩展名（见 3.3 节） |
| `filename` | TEXT | NOT NULL | 生成的文件名，如 `report.pdf`。由前端 `filename-generator.ts` 生成：优先取 Markdown 第一个 H1 标题，否则 `markdown-{timestamp}.{ext}` |
| `file_size_bytes` | INTEGER | 可空 | 输出文件大小（字节）。PDF/Word 从后端 `Content-Length` 获取；HTML 为 `new Blob([html]).size`。转换失败时为 NULL |
| `source_size_bytes` | INTEGER | 可空 | 源 Markdown 字节数（`new Blob([markdown]).size`），便于后续分析使用模式 |
| `status` | TEXT | NOT NULL, DEFAULT 'success' | `'success'` 或 `'failed'`。HTML 永远为 `'success'`（纯前端逻辑不会失败）；PDF/Word 可能因后端超时/错误而 `'failed'` |
| `created_at` | TIMESTAMPTZ | NOT NULL, DEFAULT now() | Dashboard 按此字段倒序展示 |

### 3.2 daily_usage 字段详解

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `id` | UUID | PK, 自动生成 | 记录唯一标识 |
| `user_id` | UUID | NOT NULL, FK→auth.users, CASCADE | 级联删除 |
| `usage_date` | DATE | NOT NULL, DEFAULT CURRENT_DATE | 使用日期（UTC），与 `user_id` 组成唯一约束 |
| `pdf_word_count` | INTEGER | NOT NULL, DEFAULT 0 | 当天 PDF+Word 成功转换次数。**不含 HTML**——HTML 无限制，无需计数 |
| `created_at` | TIMESTAMPTZ | NOT NULL, DEFAULT now() | 该日期记录首次创建时间 |
| `updated_at` | TIMESTAMPTZ | NOT NULL, DEFAULT now() | 最近一次递增时间，由触发器自动维护（见 2.3 节） |

### 3.3 format 字段值与文件扩展名映射

`format` 存储的是**语义名称**而非文件扩展名，保持一致性：

| format 值 | 文件扩展名 | 生成方式 | 写入 daily_usage |
|-----------|-----------|---------|-----------------|
| `'pdf'` | `.pdf` | 后端 Puppeteer | 是（计入 pdf_word_count） |
| `'word'` | `.docx` | 后端 docx 包 | 是（计入 pdf_word_count） |
| `'html'` | `.html` | 纯前端 unified | 否（HTML 无限制） |

### 4.2 关系说明

| 关系 | 类型 | 说明 |
|------|------|------|
| auth.users → conversion_history | 一对多 | 一个用户有 0~N 条转换记录 |
| auth.users → daily_usage | 一对多（受 UNIQUE 约束） | 每用户每天最多一条记录 |
| conversion_history ↔ daily_usage | **无直接外键** | 通过 `user_id` 间接关联，前端应用层保证写入一致性 |

**级联删除**：两张表均设置 `ON DELETE CASCADE`，Supabase 中删除用户时自动清除关联数据。

## 5. 数据流与读写场景说明

### 5.1 场景 A：登录用户转 PDF/Word

**触发**：用户已登录，点击 "Convert to PDF" 或 "Convert to Word"，后端返回 HTTP 200

```
前端                           Supabase DB                      Render 后端
  │                                │                                │
  │── SELECT daily_usage ─────────→│                                │
  │   WHERE user_id=me             │                                │
  │   AND usage_date=today         │                                │
  │←─ pdf_word_count: 3 ──────────│                                │
  │                                │                                │
  │   3 < 5 → 允许转换                                              │
  │                                │                                │
  │── POST /api/convert/pdf ──────────────────────────────────────→│
  │←─ 200 + PDF 文件流 ──────────────────────────────────────────←│
  │                                │                                │
  │   触发浏览器下载               │                                │
  │                                │                                │
  │── UPSERT daily_usage ─────────→│  pdf_word_count: 3 → 4        │
  │── INSERT conversion_history ──→│  (format='pdf', status='success')
  │                                │                                │
```

**关键 SQL**：

```sql
-- 1. 检查今日用量（转换前）
SELECT pdf_word_count FROM public.daily_usage
WHERE user_id = auth.uid() AND usage_date = CURRENT_DATE;
-- 返回 NULL → 今日未使用过，剩余 5 次

-- 2. 递增用量（仅成功时执行）
INSERT INTO public.daily_usage (user_id, usage_date, pdf_word_count)
VALUES (auth.uid(), CURRENT_DATE, 1)
ON CONFLICT (user_id, usage_date)
DO UPDATE SET pdf_word_count = daily_usage.pdf_word_count + 1;

-- 3. 记录转换历史
INSERT INTO public.conversion_history
  (user_id, format, filename, file_size_bytes, source_size_bytes, status)
VALUES
  (auth.uid(), 'pdf', 'report.pdf', 102400, 5200, 'success');
```

**失败场景**：后端返回 500/超时 → 前端不执行步骤 2（不扣量），但仍执行步骤 3（status='failed'）。

**写入顺序**：先 UPSERT daily_usage（更重要，控制限额），再 INSERT conversion_history（锦上添花）。如果第二步失败，仅 Dashboard 少一条记录，不影响限额功能。

### 5.2 场景 B：登录用户转 HTML

**触发**：用户已登录，点击 "Convert to HTML"（纯前端完成，零后端调用）

```
前端                           Supabase DB
  │                                │
  │   unified(remark+rehype)       │
  │   本地生成 HTML 字符串          │
  │   触发浏览器下载               │
  │                                │
  │── INSERT conversion_history ──→│  (format='html', status='success')
  │                                │
  │   不操作 daily_usage           │  ← HTML 无限制
  │                                │
```

- HTML 转换**必须写入** conversion_history（产品文档 Dashboard 线框图展示了 HTML 记录 `🌐 HTML readme.html`）
- HTML 转换**不写入** daily_usage（HTML 不受配额限制）
- HTML 的 `status` 始终为 `'success'`（纯前端渲染不存在服务端失败）
- HTML 的 `file_size_bytes` 存 `new Blob([htmlString]).size`（UTF-8 字节数）

### 5.3 场景 C：Dashboard 加载

**触发**：用户访问 `/en/dashboard`

```
前端                           Supabase DB
  │                                │
  │── 并行查询 ──────────────────→│
  │   ① SELECT conversion_history │  最近 50 条（全格式）
  │   ② SELECT daily_usage        │  今日 pdf_word_count
  │←─ 两份结果 ───────────────────│
  │                                │
  │   渲染：                       │
  │   - 用量进度条 (X/5 remaining) │
  │   - 历史列表（50 条）          │
  │                                │
```

**SQL**：

```sql
-- 最近 50 条转换记录（含全部三种格式）
SELECT format, filename, file_size_bytes, status, created_at
FROM public.conversion_history
WHERE user_id = auth.uid()
ORDER BY created_at DESC
LIMIT 50;

-- 今日用量
SELECT pdf_word_count FROM public.daily_usage
WHERE user_id = auth.uid() AND usage_date = CURRENT_DATE;
-- 返回 NULL → 今日剩余 5 次
-- 返回 { pdf_word_count: 3 } → 今日剩余 2 次
```

### 5.4 场景 D：匿名用户转换

**数据库零参与。** 全部限额追踪在客户端和后端内存中完成：

| 层 | 机制 | 限额 | 可绕过 |
|---|------|------|--------|
| 客户端 | localStorage `md-usage-{YYYY-MM-DD}` = `{count: N}` | 2 次/天 | 可清除/无痕模式 |
| 服务端 | express-rate-limit 内存，按 IP + 24h 滑动窗口 | 10 次/天/IP | 换 IP 可绕过 |
| 服务端超限 | HTTP 429 Too Many Requests | — | — |

匿名用户的 HTML 转换纯前端完成，无任何限制，不做任何追踪。

### 5.5 读写频率预估

| 操作 | 触发频率 | 表 | 类型 | 索引命中 |
|------|---------|-----|------|---------|
| 检查今日用量 | 每次 PDF/Word 转换前 | daily_usage | SELECT | UNIQUE 索引 |
| 递增用量 | 每次成功 PDF/Word 后 | daily_usage | UPSERT | UNIQUE 索引 |
| 写转换记录 | 每次转换后（含 HTML） | conversion_history | INSERT | — |
| 查历史列表 | 每次打开 Dashboard | conversion_history | SELECT | idx_history_user_created |
| 查今日用量 | 每次打开 Dashboard | daily_usage | SELECT | UNIQUE 索引 |

初期日活几十人，每人每天 1-3 次转换，日写入量 < 100 条。Supabase Free Tier 完全足够。

## 6. 扩展性考虑

### 6.1 V1.0 不做但已为扩展预留的空间

| 未来功能 | 数据库影响 | 扩展方式 |
|---------|-----------|---------|
| **付费订阅（Pro）** | 需新增 `subscriptions` 表或用 Supabase Auth user_metadata | `daily_usage` 的限额值由前端常量控制，改限额只需改前端代码 |
| **API 售卖** | 新增 `api_keys` + `api_usage` 表 | 独立新增，与现有 2 张表无冲突 |
| **批量转换** | conversion_history 可记录批量中每个文件 | 无需改表结构 |
| **自定义 PDF 模板** | 新增 `templates` 表 | 独立新增 |
| **更多语言 / 广告** | 无数据库影响 | 纯前端 |
| **转换耗时追踪** | conversion_history 加 `duration_ms` 列 | `ALTER TABLE ADD COLUMN`，零停机 |
| **用户来源分析** | conversion_history 加 `locale`/`user_agent` 列 | 同上 |

### 6.2 数据量增长预估

| 场景 | conversion_history 条数/年 | daily_usage 条数/年 | 总存储 |
|------|--------------------------|--------------------|----|
| 保守（50 DAU, 2 次/天） | 36,500 | 18,250 | ~11 MB |
| 乐观（500 DAU, 3 次/天） | 547,500 | 182,500 | ~146 MB |
| 极限（2000 DAU, 3 次/天） | 2,190,000 | 730,000 | ~584 MB |

- Supabase Free Tier：500 MB 存储
- 保守/乐观场景下 **3 年内无忧**
- 极限场景接近阈值时，优先清理 daily_usage 历史数据（30 天前的无查询需求）

### 6.3 数据保留策略

**V1.0 不实施主动清理。** 当数据量接近 Supabase 存储上限时：

1. **daily_usage**：可安全删除 30 天前的记录（历史日用量无业务查询需求）
2. **conversion_history**：可删除 6 个月前的记录（Dashboard 仅展示最近 50 条）
3. 实施方式：Supabase pg_cron 扩展 或 Edge Function 定时触发

## 7. 风险点与注意事项

### 7.1 技术方案文档遗漏：updated_at 触发器

**问题**：05-技术方案文档第 6.1 节定义了 `daily_usage.updated_at DEFAULT now()`，但未定义 UPDATE 触发器。执行 `ON CONFLICT DO UPDATE SET pdf_word_count = pdf_word_count + 1` 时，`updated_at` 不会自动更新。

**修复**：本文档第 2.3 节补充了 `handle_updated_at()` 触发器。

### 7.2 技术方案文档问题：冗余索引

**问题**：05-技术方案文档为 daily_usage 创建了 `idx_usage_user_date ON (user_id, usage_date)` 索引，但 `UNIQUE(user_id, usage_date)` 约束已自动创建等效唯一索引。两份索引完全冗余。

**修复**：本文档第 2.2 节删除了显式索引，仅保留 UNIQUE 约束自带的索引。

### 7.3 技术方案文档问题：RLS 粒度过粗

**问题**：05-技术方案文档对 daily_usage 使用 `FOR ALL` 策略，允许 SELECT/INSERT/UPDATE/DELETE 全部操作。用户可通过 Supabase Client SDK 直接 DELETE 自己的 daily_usage 记录，重置配额。

**影响**：V1.0 全免费，用户"作弊"只是多用几次免费转换，无金钱损失。但仍应收紧。

**修复**：本文档第 2.2 节拆分为 SELECT + INSERT + UPDATE 三条策略，不提供 DELETE。

### 7.4 前端双表写入无事务保证

**问题**：场景 A 中，成功转换后前端分两步写入 daily_usage 和 conversion_history。两个请求无原子性保证。

**影响分析**：

| 失败情况 | 后果 | 严重程度 |
|---------|------|---------|
| daily_usage 写入成功，conversion_history 失败 | 扣了量但 Dashboard 少一条记录 | 低 |
| daily_usage 写入失败，conversion_history 成功 | 没扣量（用户多得一次） | 低 |

**V1.0 策略**：接受此风险（概率极低 + 影响轻微）。写入顺序固定为 daily_usage 优先。V2.0 如需更严格一致性，可用 Supabase RPC（PostgreSQL 函数）封装为单个事务。

### 7.5 时区与日期重置

**问题**：`daily_usage.usage_date` 使用 `DEFAULT CURRENT_DATE`，取决于 Supabase PostgreSQL 的 timezone 设置（默认 UTC）。不同时区的用户在本地"同一天"可能被 DB 拆成两天。

**V1.0 策略**：统一使用 UTC。产品文档已明确 Dashboard 显示 "resets daily at midnight UTC"，用户知晓重置时间为 UTC 午夜。

### 7.6 HTML 转换的 file_size_bytes 语义

**问题**：PDF/Word 的 `file_size_bytes` 从后端响应 `Content-Length` 获取，但 HTML 是纯前端生成的字符串。

**约定**：HTML 的 `file_size_bytes` 存 `new Blob([htmlString]).size`（UTF-8 编码字节数）。三种格式统一用 Blob 计算，保持 Dashboard 展示一致。

### 7.7 Supabase Auth 用户元数据

**说明**：V1.0 不读写 `auth.users` 表的 `raw_user_meta_data` 字段。如果 V2.0 需要存储用户偏好（如默认导出格式、语言偏好），可以使用此字段，无需新建表。
