## 1. 技术目标

### 1.1 性能目标

| 指标 | 目标值 | 说明 |
|------|--------|------|
| Lighthouse Performance | ≥ 90 | 全部核心页面（工具页+指南页） |
| Lighthouse SEO | ≥ 90 | 全部 index 页面 |
| 首屏可交互时间 (TTI) | 工具页 < 3s / 指南页 < 2s | CodeMirror 异步加载，不阻塞首屏 |
| PDF 生成时间 | 常规 < 5s / 极端 < 15s / 硬超时 30s | "常规"指 < 50KB Markdown |
| JS Bundle（首页） | < 200KB gzipped | CodeMirror 通过 dynamic import 异步加载 |
| 字体加载 | ≤ 120KB (woff2) | Inter + JetBrains Mono |

### 1.2 成本目标

| 项目 | 费用 | 说明 |
|------|------|------|
| Vercel | $0/月 | Free Tier（100GB 带宽/月，足够前期） |
| Render | $7-25/月 | 起步 Starter ($7)，压测不够升 Standard ($25) |
| Supabase | $0/月 | Free Tier（500MB 存储，50K MAU） |
| 域名 | ~$1.67/月 | .app ~$20/年 |
| **合计** | **$8.67-26.67/月** | 视 Render 实例级别而定 |

### 1.3 可扩展性目标

- 架构支持后续增加语言（ja/ko/es 等）无需重构
- 后端 API 模块化，支持后续增加 AI 功能、批量转换、API 售卖
- 前端组件化，支持后续增加 PDF 模板选择、暗色模式

## 2. 技术栈

### 2.1 前端（Vercel 部署）

| 类目 | 选型 | 版本 | 理由 |
|------|------|------|------|
| 框架 | Next.js | 16.x | App Router + RSC，SEO 友好 |
| UI 库 | React | 19.x | Next.js 16 内置 |
| 语言 | TypeScript | 5.7+ | 类型安全，前后端共享类型 |
| CSS | Tailwind CSS | 4.x | 原子化，与 UI 规范 8px 网格兼容 |
| 编辑器 | CodeMirror 6 | @codemirror/view 6.x | Markdown 模式，语法高亮 |
| Markdown 渲染 | unified (remark + rehype) | remark-parse 11.x, rehype-stringify 10.x | GFM 支持，插件丰富，前后端共用 |
| Markdown 预览 CSS | github-markdown-css | 5.x | GitHub 风格，与 PDF 输出一致 |
| 图标 | lucide-react | 0.460+ | 线性风格统一 |
| 字体 | next/font | 内置 | Inter + JetBrains Mono，自动优化 |
| 文件编码检测 | jschardet | 3.x | 检测 GBK/Shift-JIS 等 |
| 编码转换 | iconv-lite（浏览器版） | 0.6+ | GBK → UTF-8 |
| Supabase SDK | @supabase/supabase-js + @supabase/ssr | 2.x | Auth + DB 客户端 |
| 状态管理 | 无（useState + sessionStorage） | — | 12 页小站不需要 Redux/Zustand |

### 2.2 后端（Render 部署）

| 类目 | 选型 | 版本 | 理由 |
|------|------|------|------|
| 运行时 | Node.js | 22 LTS | 与前端一致 |
| 框架 | Express | 5.x | 轻量、生态成熟 |
| PDF 生成 | Puppeteer | 23.x | Chrome headless 渲染 |
| Word 生成 | docx | 9.x | 纯 JS 生成 .docx |
| Markdown → HTML | unified (remark + rehype) | 同前端 | 后端也需解析 Markdown 为 HTML |
| 速率限制 | express-rate-limit | 7.x | IP 级别限制 |
| CORS | cors | 2.x | 限制仅允许 markdown-to-pdf.app 源 |
| 请求体限制 | Express 内置 json limit | — | 限制 500KB |

### 2.3 数据库与认证

| 类目 | 选型 | 说明 |
|------|------|------|
| Auth | Supabase Auth | Email + Google OAuth |
| DB | Supabase PostgreSQL | 转换历史、用量追踪 |
| ORM | 无 | 直接用 Supabase 客户端 SDK 操作，不需要 Prisma/Drizzle |

### 2.4 不使用的技术（明确排除）

| 技术 | 不用原因 |
|------|---------|
| Redux / Zustand | 12 页工具站无全局状态需求 |
| Prisma / Drizzle | Supabase SDK 直接操作足够 |
| Docker Compose | 开发环境不需要容器化，生产仅后端用 Docker |
| Redis | V1.0 限流用内存存储足够 |
| AWS/GCP | 成本过高，Vercel + Render + Supabase 组合更经济 |
| markdown-it | unified 生态更现代，GFM 支持更好 |

### 3.2 三端职责划分

| 端 | 职责 | 明确不做的事 |
|----|------|------------|
| **Vercel 前端** | 页面渲染(SSR+CSR)、编辑器、预览、HTML 导出、Auth UI、SEO、i18n | 不做 PDF/Word 生成 |
| **Render 后端** | PDF 生成、Word 生成、IP 限流、Puppeteer 管理 | 不做页面渲染、不存储用户数据 |
| **Supabase** | Auth、用户数据、转换历史、登录用户用量追踪 | 不做文件存储（不存 PDF/Word 文件） |

### 3.3 关键架构决策

**前端直接调 Render 后端，不通过 Vercel API Routes 中转。** 理由：
1. Vercel Serverless 有 10 秒超时（Free Tier），无法支撑 30 秒 PDF 生成
2. 减少一跳网络延迟
3. 二进制文件流无需在 Vercel 中转

## 5. 数据流转说明

### 5.1 场景 1：匿名用户粘贴转 PDF

```
1. 用户粘贴 Markdown 到 CodeMirror 编辑器
2. CM6 onChange → debounce 300ms → unified 解析 → HTML → 预览面板渲染
3. 同时：内容写入 sessionStorage（key: "md-editor-content"）
4. 用户点击 "Convert to PDF"
5. 前端检查 localStorage 用量（key: "md-usage-{YYYY-MM-DD}"）
   ├── count >= 2 → 内联提示 "Sign up to Convert"（按钮变灰）
   └── count < 2 → 继续
6. POST { markdown: string } → Render /api/convert/pdf
7. Render express-rate-limit 检查 IP
   ├── 超限 → 429 响应 → 前端显示 "请明天再来"
   └── 未超限 → 继续
8. Render: markdown → unified → HTML string
9. Render: browser-pool 取 Page → page.setContent(HTML + github-markdown.css + page-break.css)
10. Render: page.pdf({ format: 'A4', margin }) → PDF Buffer
11. Response: Content-Type: application/pdf, Content-Disposition: attachment; filename="xxx.pdf"
12. 前端收到 200 → 创建 Blob URL → 触发 <a download> → 用户下载
13. 前端递增 localStorage 用量计数
```

### 5.2 场景 2：登录用户转 Word

```
1-4. 同场景 1（编辑 → 预览 → 点转换）
5. 前端从 Supabase Session 获取 JWT
6. 前端查 Supabase daily_usage 表，检查今日 pdf_word_count
   ├── count >= 5 → "Today's limit reached. Come back tomorrow."
   └── count < 5 → 继续
7. POST { markdown } + Authorization: Bearer <JWT> → Render /api/convert/word
8. Render: markdown → unified → remark AST → 遍历 AST 节点 → docx 包构建段落/表格/代码块
9. Response: Content-Type: application/vnd.openxmlformats-officedocument.wordprocessingml.document
10. 前端触发下载
11. 前端 INSERT INTO conversion_history (user_id, format, filename, file_size_bytes, status)
12. 前端 UPSERT daily_usage SET pdf_word_count = pdf_word_count + 1 WHERE usage_date = today
```

### 5.3 场景 3：格式切换（PDF → Word）

```
1. 用户在 /en/（PDF 页）编辑了内容
2. 点击格式切换器 "Word"（Next.js <Link href="/en/to-word/">）
3. 点击瞬间：format-switcher.tsx 触发 sessionStorage.setItem("md-editor-content", 当前内容)
4. Next.js 客户端导航（无整页刷新）→ /en/to-word/ 页面
5. to-word/page.tsx mount → useEditorContent hook 从 sessionStorage 读取 → 填充编辑器
6. 用户看到内容无缝保留
7. 格式切换器高亮变为 "Word"（蓝色），转换按钮变为 "Convert to Word"（蓝色）
```

### 5.4 场景 4：MiniEditor CTA → 工具页

```
1. 用户在 /en/guides/markdown-new-line 的 MiniEditor 中编辑了内容
2. 点击 "Convert to PDF →" CTA
3. CTA 触发 sessionStorage.setItem("md-editor-content", MiniEditor 当前内容)
4. Next.js Link 导航到 /en/
5. 首页 mount → 检测 sessionStorage 有内容 → 填充编辑器（覆盖预填示例）
6. 用户看到自己在指南页的内容 + 预览
```

### 5.5 场景 5：.md 文件上传

```
1. 用户拖拽 .md 文件到 FileDropzone
2. FileReader.readAsArrayBuffer(file) → 获取原始字节
3. jschardet.detect(buffer) 检测编码
   ├── UTF-8（或 ASCII）→ TextDecoder('utf-8').decode(buffer)
   └── GBK/Shift-JIS 等 → iconv-lite.decode(buffer, detectedEncoding)
4. 解码后的文本填充到 CodeMirror
5. 触发预览更新（debounce 300ms → unified 渲染）
6. 同时更新 sessionStorage
```

### 5.6 API 响应规范

#### 成功响应（PDF）

```
HTTP/1.1 200 OK
Content-Type: application/pdf
Content-Disposition: attachment; filename="report.pdf"
Content-Length: 102400

<binary PDF data>
```

#### 成功响应（Word）

```
HTTP/1.1 200 OK
Content-Type: application/vnd.openxmlformats-officedocument.wordprocessingml.document
Content-Disposition: attachment; filename="report.docx"
Content-Length: 51200

<binary docx data>
```

#### 失败响应

```json
// 400 Bad Request — 输入无效（空内容、非法格式）
{ "error": "INVALID_INPUT", "message": "Markdown content is required." }

// 413 Payload Too Large — 超过 500KB
{ "error": "PAYLOAD_TOO_LARGE", "message": "Content exceeds 500KB limit." }

// 429 Too Many Requests — IP 限流
{ "error": "RATE_LIMITED", "message": "Daily limit exceeded. Try again tomorrow." }

// 500 Internal Server Error — Puppeteer/docx 生成失败
{ "error": "CONVERSION_FAILED", "message": "Failed to generate PDF. Please try again." }

// 504 Gateway Timeout — 超过 30 秒
{ "error": "TIMEOUT", "message": "Conversion timed out. Try shorter content." }
```

前端根据 HTTP 状态码处理：2xx 触发下载，4xx/5xx 显示错误提示 + 重试按钮。

**表 2：daily_usage**（登录用户每日用量）

```sql
CREATE TABLE daily_usage (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  usage_date DATE NOT NULL DEFAULT CURRENT_DATE,
  pdf_word_count INTEGER NOT NULL DEFAULT 0,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE(user_id, usage_date)
);

-- UNIQUE(user_id, usage_date) 已自动创建索引，无需额外建索引

ALTER TABLE daily_usage ENABLE ROW LEVEL SECURITY;

CREATE POLICY "Users can view own usage"
  ON daily_usage FOR SELECT
  USING (auth.uid() = user_id);

CREATE POLICY "Users can insert own usage"
  ON daily_usage FOR INSERT
  WITH CHECK (auth.uid() = user_id);

CREATE POLICY "Users can update own usage"
  ON daily_usage FOR UPDATE
  USING (auth.uid() = user_id)
  WITH CHECK (auth.uid() = user_id);

-- 注意：不创建 DELETE 策略，防止用户删除记录绕过限额
```

**updated_at 自动更新触发器**：

```sql
CREATE OR REPLACE FUNCTION public.handle_updated_at()
RETURNS TRIGGER AS $$
BEGIN
  NEW.updated_at = now();
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER on_daily_usage_updated
  BEFORE UPDATE ON public.daily_usage
  FOR EACH ROW
  EXECUTE FUNCTION public.handle_updated_at();
```

### 6.2 匿名用户用量追踪

匿名用户不入库，采用双重检查：

| 层 | 实现 | 作用 | 可绕过 |
|----|------|------|--------|
| **客户端** | localStorage `md-usage-{YYYY-MM-DD}` = `{count: N}` | 即时 UI 反馈 | 可清除/无痕模式 |
| **服务端** | express-rate-limit 内存存储，按 IP + 日期窗口 | 真正限制 | 换 IP 可绕过 |

IP 限流参数：
- 同 IP 每日 PDF+Word 请求上限：**10 次**（比单用户 2 次宽裕 5 倍，缓解共享 IP 误伤）
- 窗口：24 小时滑动窗口
- 超限返回 429

### 6.3 关键规则：转换失败不扣量

实现方式：
- 前端发起转换请求 → 等待后端响应
- 仅当后端返回 HTTP 200 + 有效文件流时，前端才递增用量计数
- 后端超时/500/网络错误 → 前端不递增，显示友好错误 + 重试按钮

### 6.4 文件名生成逻辑

```typescript
// lib/converter/filename-generator.ts
function generateFilename(markdown: string, format: 'pdf' | 'word' | 'html'): string {
  // 1. 尝试提取第一个 H1 标题
  const h1Match = markdown.match(/^#\s+(.+)$/m);
  if (h1Match) {
    const title = h1Match[1]
      .replace(/[^\w\s-]/g, '')  // 去除特殊字符
      .trim()
      .replace(/\s+/g, '-')     // 空格转连字符
      .toLowerCase()
      .slice(0, 50);            // 限制长度
    return `${title}.${format === 'word' ? 'docx' : format}`;
  }
  // 2. 无标题，用时间戳
  const timestamp = Date.now();
  return `markdown-${timestamp}.${format === 'word' ? 'docx' : format}`;
}
```

## 11. 风险点与技术注意事项

### P0 — 必须在开发期间解决

**风险 1：Render 内存不足导致 Puppeteer 崩溃**

| 维度 | 说明 |
|------|------|
| 场景 | Starter 512MB：Chromium ~200-300MB + Node.js ~150MB，几乎没有余量 |
| 缓解 | 浏览器池**最多 1 个**实例，复用 Page 不复用 Browser；使用 `--disable-dev-shm-usage --no-sandbox --single-process`；每次生成后关 Page |
| 监控 | 开发阶段用 `process.memoryUsage()` log 每次 PDF 生成的内存峰值 |
| 决策点 | 如单次峰值 > 400MB → 必须升到 Standard ($25/月 2GB) |

**风险 2：CJK 字体缺失（PDF 方块字）**

| 维度 | 说明 |
|------|------|
| 场景 | 用户粘贴中文/日文/韩文 Markdown 转 PDF |
| 方案 | Dockerfile 安装 `fonts-noto-cjk`（~120MB 镜像增量，一次性） |
| 验证 | 开发阶段用中/日/韩混合文本生成测试 PDF |

**风险 3：CodeMirror 6 移动端粘贴兼容性**

| 维度 | 说明 |
|------|------|
| 场景 | iOS Safari / Chrome Android 粘贴行为异常 |
| 方案 | 渐进增强——页面先渲染 `<textarea>`，CodeMirror 异步加载后替换。如 CM6 加载失败或兼容性问题，保留 textarea |
| 测试 | iOS Safari 17+、Chrome Android 120+、Samsung Browser 25+ |

**风险 4：PDF 生成超时**

| 维度 | 说明 |
|------|------|
| 方案 | Puppeteer `page.pdf()` 设 30 秒超时；Express 路由设 35 秒超时（多 5 秒清理） |
| 前端 | 点击后立即显示 "Generating your PDF..."；超时后 "This is taking longer than expected. Please try again." + Retry 按钮 |
| 规则 | 超时/失败 → 不扣用量 |

### P1 — 显著影响体验

**风险 5：Word 生成质量**
- `docx` 包对嵌套列表、复杂表格、代码块高亮支持有限
- 开发阶段准备 20+ 种 Markdown 测试用例
- 不支持的格式降级为纯文本段落（不崩溃/不乱码）
- 后续可考虑切换到 Pandoc（需 Docker 内安装）

**风险 6：超长内容性能**
- CM6 对 100K+ 字符已有虚拟化渲染，性能问题主要在预览端
- 实时预览 debounce 300ms
- 后端设请求体上限 500KB（超过返回 413）
- 超长预览（> 200KB）考虑截断 + 提示 "Content truncated in preview"

**风险 7：Render 冷启动**
- Starter 实例 15 分钟无请求会 spin down
- 首次请求可能等 30-60 秒（启动 Node + Chromium）
- 缓解：配置 Health Check（/health），Render 会定期 ping
- 备用：UptimeRobot 免费每 5 分钟 ping 后端保活

### P2 — 体验细节

**风险 8：sessionStorage 容量**
- 浏览器一般限制 5-10MB，500KB Markdown 绰绰有余
- 超大内容（> 1MB）仍尝试存储，失败时静默忽略

**风险 9：匿名限流误伤共享 IP**
- IP 限制设宽松（同 IP 10 次/天，单用户实际只有 2 次）
- 真正限制靠 localStorage（浏览器级别）
- V1.0 接受无痕模式绕过的现实

**风险 10：.md 文件编码检测误判**
- jschardet 对短文本准确率不够高
- 策略：先用 UTF-8 解码，如出现连续 `\uFFFD`（替换字符），再用 jschardet 猜测编码

## 附录 A：Puppeteer 浏览器池实现参考

```typescript
// backend/src/services/browser-pool.ts
import puppeteer, { Browser } from 'puppeteer';

let browser: Browser | null = null;

export async function getBrowser(): Promise<Browser> {
  if (!browser || !browser.connected) {
    browser = await puppeteer.launch({
      executablePath: process.env.PUPPETEER_EXECUTABLE_PATH || '/usr/bin/chromium',
      headless: true,
      args: [
        '--no-sandbox',
        '--disable-setuid-sandbox',
        '--disable-dev-shm-usage',
        '--single-process',
        '--disable-gpu',
        '--no-zygote',
      ],
    });
  }
  return browser;
}

export async function closeBrowser(): Promise<void> {
  if (browser) {
    await browser.close();
    browser = null;
  }
}

// 进程退出时清理
process.on('SIGTERM', closeBrowser);
process.on('SIGINT', closeBrowser);
```
