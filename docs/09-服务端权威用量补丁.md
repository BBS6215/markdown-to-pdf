## 1. 背景与问题

06-数据库设计说明 §5.1 定义的扣额数据流为：

```
前端浏览器 → SELECT daily_usage（check）→ POST /api/convert/pdf → ... → 浏览器 UPSERT daily_usage
```

即**扣额逻辑跑在浏览器里**，由浏览器 Supabase Client 直接 UPSERT。问题：

1. **可绕过**：用户可以拒绝执行 UPSERT 那一行 JS（开 devtools 改逻辑、装拦截扩展），转换照常完成但不扣额。
2. **并发不安全**：同时打开两个标签页，两个 SELECT 都看到 `count=4`，两个 UPSERT 都执行，最终 count 上升到 5 而非 6——但更糟的是边界处可直接超额。
3. **HTTP 上没扣额权威记录**：服务端 IP rate limit 是 10 次/天/IP，攻击者用一个账户多机协作可消耗服务端转换资源远超 5 次。

## 2. 修复设计：后端权威 + JWT 验证

### 2.1 三件套（DB migration `server_authoritative_quota`）

| 物件 | 用途 | 权限 |
|---|---|---|
| `consume_quota(uuid, text, int) RETURNS jsonb` | 原子扣额（INSERT ON CONFLICT WHERE count<limit RETURNING） | SECURITY DEFINER, **仅 service_role 可执行** |
| `refund_quota(uuid, text) RETURNS void` | 转换失败时退回 1 次 | SECURITY DEFINER, **仅 service_role 可执行** |
| `record_conversion(...)` | 写 conversion_history | SECURITY DEFINER, **仅 service_role 可执行** |

同时撤销 `daily_usage` 的两条 RLS：
- `"Users can insert own usage"` → DROPPED
- `"Users can update own usage"` → DROPPED

`daily_usage` 的 SELECT RLS 保留（Dashboard 仍能读自己今日用量）。
`conversion_history` 的 INSERT RLS 保留（HTML 转换在前端记录历史，docs/06 §5.2 已定义）。

### 2.2 原子扣额 SQL 核心

```sql
INSERT INTO public.daily_usage (user_id, usage_date, pdf_word_count)
VALUES (p_user_id, CURRENT_DATE, 1)
ON CONFLICT (user_id, usage_date) DO UPDATE
  SET pdf_word_count = daily_usage.pdf_word_count + 1
  WHERE daily_usage.pdf_word_count < p_limit
RETURNING pdf_word_count;
```

PostgreSQL 在 `ON CONFLICT DO UPDATE` 时持有目标行的行级排它锁；`WHERE` 子句失败时 `RETURNING` 为空。并发下：
- 第 1 个事务 4→5：成功
- 第 2 个并发事务等待行锁释放后看到 count=5，WHERE 失败，RETURNING 空 → 函数返回 `allowed: false`

无超额可能。

### 2.3 转换流程

```
POST /api/convert/{pdf,word}
Headers: Authorization: Bearer <supabase access_token>   (可选)

  middleware attachUser
    └─ 有 token → 用 anon key + auth.getUser(token) 验证 → req.user
    └─ 无 / 失败 → req.user = null

  middleware convertRateLimiter
    └─ skip: req.user 非 null → 跳过（登录用户走 user 维度配额）
    └─ 否则按 IP/24h 限流

  route handler
    1. 若 req.user：consume_quota(user.id, format)，allowed=false → 429
    2. generatePdf / generateWord
    3. 成功 → record_conversion(success)；失败 → refund_quota + record_conversion(failed)
```

### 2.4 失败回滚

转换失败（Puppeteer crash、超时、内存爆等）必须**退回已扣的 1 次**——否则用户被白白吃额度，docs/06 §5.1 明确"失败不扣量"。本补丁通过 `refund_quota` 实现。

## 6. 验证用例

| # | 场景 | 期望 |
|---|---|---|
| 1 | 匿名调 PDF | 走 IP rate limit，limit 不变 |
| 2 | 登录用户调 PDF 5 次 | 5 次成功，第 6 次 429 + body `{error: 'RATE_LIMITED'}` |
| 3 | 登录用户 PDF 转换超时 | `refund_quota` 调用，第 6 次仍可尝试 |
| 4 | 浏览器尝试 `supabase.from('daily_usage').insert(...)` | RLS 拒绝（403/policy violation） |
| 5 | 浏览器尝试 `supabase.from('conversion_history').insert(...)`（HTML） | 通过（policy 保留） |
| 6 | 浏览器尝试 `supabase.rpc('consume_quota', ...)` | 403/permission denied（仅 service_role 可调） |

## 7. 与 06-数据库设计说明的差异

| 06 原设计 | 09 补丁 | 状态 |
|---|---|---|
| daily_usage 由浏览器 UPSERT | 由后端 service_role 调 RPC | 替换 |
| RLS: daily_usage SELECT + INSERT + UPDATE | RLS: 仅保留 SELECT | 收紧 |
| 失败不扣量（前端跳过 UPSERT） | 失败 refund_quota 退回（已扣需要回滚） | 等价语义，机制不同 |
| 并发依赖前端写入顺序 | 后端 PG `ON CONFLICT WHERE count<limit` 原子 | 强化 |
| HTML 由前端 INSERT conversion_history | 保留，但 INSERT policy 收紧到 `format = 'html'`（migration 20260513122753） | 收紧 |

如 06 与本补丁冲突，**以本补丁为准**。
