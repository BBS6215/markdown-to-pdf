## 1. 核心用户任务路径

### 1.1 关键认知前提：用户的认知光谱

产品结构文档中所有流程隐含了一个假设——用户知道自己手里的东西叫"Markdown"。但目标用户实际上分布在一个认知光谱上：

| 认知层级 | 用户画像 | 心智模型 | 占比估计 |
|---------|---------|---------|---------|
| **完全不知道** | 普通 AI 工具使用者 | "ChatGPT 给我一坨带星号和井号的乱文本" | 40-50% |
| **听说过但不确定** | 偶尔接触技术文档的人 | "好像叫 Markdown？那些 # 和 ** 符号" | 20-30% |
| **知道但不会写** | 产品经理、技术写手 | "我知道是 Markdown，帮我转成 PDF 就行" | 15-20% |
| **熟练使用** | 程序员、开发者 | "我要把 README.md 转成 PDF" | 10-15% |

**核心策略：分层呈现，一眼扫过每个认知水平的人都能找到锚点。**

### 1.2 已确认的文案策略

#### 首屏 sub-heading（H1 下方，已确认文案）

| 格式 | English | 中文 |
|------|---------|------|
| PDF | `Paste Markdown, preview it live, and export a PDF in your browser — no signup or upload.` | `粘贴 Markdown，实时预览并在浏览器中导出 PDF；无需注册，内容不会上传。` |
| Word | `Paste Markdown, preview it live, and download a Word (.docx) file — no signup or upload.` | `粘贴 Markdown，实时预览并下载 Word（.docx）；无需注册，内容不会上传。` |
| HTML | `Paste Markdown, preview it live, and copy clean HTML — no signup or upload.` | `粘贴 Markdown，实时预览并复制干净的 HTML；无需注册，内容不会上传。` |

- 每页只显示对应格式的一句，不叠加第二段 intro。
- 句子同时覆盖输入、实时预览、目标输出和隐私/注册顾虑。
- 不再用额外模块解释操作步骤；真正的反馈来自粘贴后的实时预览。

#### 编辑器 placeholder

```
Paste your Markdown or AI text here — supports text from ChatGPT, Claude, Notion, or any .md file
```

#### 编辑器面板标题

- 左侧：**Markdown Input**（下方小字 "Paste from ChatGPT, Claude, or any text editor"）
- 右侧：**Live Preview**

#### 编辑器初始状态

- 首次访问不预填示例内容，编辑器为空，只显示明确的 placeholder。
- 同一标签页中已有 sessionStorage 内容时恢复，用于格式切换和指南 CTA 内容传递。
- 不使用 localStorage `hasVisited`，也不为首次访问和回头用户维护两套页面。
- 极简不是“不给提示”：H1 下的一句话必须同时说明输入、实时预览、目标输出和无需注册/上传。

### 1.3 新用户首次使用路径（非技术用户视角）

```
用户从 AI 工具复制了一段"格式混乱"的文本
    │
    ▼
通过搜索/推荐进入 markdown-to-pdf.app
    │
    ▼
【认知关卡 1】看到 H1 + sub-heading → 0.5 秒确认"来对地方了"
    │
    ▼
看到空编辑器 + 明确 placeholder → 直接粘贴
    │
    ▼
粘贴自己的内容
    │
    ▼
【认知关卡 2】右侧 Live Preview 渲染出干净格式 → "这就是我要的效果！"
    │
    ▼
【认知关卡 3】转换按钮 + 用量提示 → 理解可以下载，知道剩余次数
    │
    ▼
点击 "Convert to PDF" → 下载成功
    │
    ▼
【关键决策点】是否收藏/记住这个网站
```

### 1.4 回头用户路径

```
从书签/直接输入域名进入
    │
    ▼
编辑器空白（上次内容不保留——隐私考虑）
    │
    ▼
直接粘贴 → 预览 → 转换 → 下载（10 秒内完成）
```

**回头用户的差异化需求**：
- 当前标签页存在 sessionStorage 内容时恢复，便于跨格式继续转换
- 没有 sessionStorage 内容时仍显示空编辑器，不以 localStorage `hasVisited` 区分用户
- 页面结构和首次访问保持一致，避免记忆两套交互

### 1.5 移动端用户路径（高风险场景）

大量用户在手机上使用 ChatGPT → 得到 Markdown 输出 → 想转 PDF 发给别人。**整个操作在手机上完成**。

```
手机复制 AI 输出
    │
    ▼
浏览器打开网站
    │
    ▼
【高风险】在 CodeMirror 编辑器中粘贴
（移动端富文本编辑器的粘贴体验参差不齐）
    │
    ▼
切换到预览 Tab 查看效果
    │
    ▼
点转换 → 下载（移动浏览器文件下载体验不一致）
```

这是必须在开发阶段重点测试的路径。

## 2. 各关键流程的体验评估

### 流程 1：粘贴转换（最高频）

| 步骤 | 潜在卡点 | 严重程度 | 说明 |
|------|---------|---------|------|
| 打开首页 | 用户是否立刻知道输入位置 | 低 | 空编辑器保留明确 placeholder，H1 下的一句话说明输入、预览、输出和隐私 |
| 粘贴内容 | 是否需要先清理页面自带内容 | 无 | 首次访问不预填示例，粘贴直接成为编辑器内容 |
| 预览渲染 | 粘贴纯文本（非 Markdown）会怎样？ | 低 | 纯文本预览也正常显示，只是没有格式化，不会报错 |
| 点击转换 | 长内容时转换按钮可能滚出视窗 | 中 | **转换按钮应在桌面端始终可见（fixed 定位）** |
| 下载文件 | 自动生成的文件名对用户无意义 | 低 | 取 H1 标题作为文件名，无标题用 `markdown-{timestamp}.{ext}` |

### 流程 2：上传转换

| 端 | 交互方式 | 注意点 |
|----|---------|--------|
| 桌面端 | 拖拽 .md 文件 + 点击 Upload 按钮 | 拖拽区域需视觉反馈（虚线边框+蓝色高亮） |
| 移动端 | 仅 Upload 按钮，触发系统文件选择器 | 移动端不存在拖拽操作；iOS 文件选择器能否选到 .md 文件需测试 |

**额外风险**：上传的 .md 文件编码不是 UTF-8（Windows 用户可能产生 GBK 文件），解析后会乱码。需做编码检测和自动转换。

### 流程 3：语法查阅 → 转换（SEO 引流路径）

**CTA 转化率可能低的三个原因及对策**：

| 原因 | 说明 | 优化建议 |
|------|------|---------|
| 意图不匹配 | 搜 "markdown new line" 的用户当下需求是学语法，不是转换 | CTA 强调"导出/下载"价值而非"去编辑器" |
| 迷你编辑器太好用 | 已满足"试试语法"的需求，无动力跳转 | CTA 文案改为 "Export as PDF →"（直觉：导出我刚试好的内容） |
| CTA 缺乏场景感 | 通用问句 "Need to convert?" 不够有吸引力 | 结合指南内容定制文案，如 "Got your formatting right? **Download it as a clean PDF** →" |

**CTA 位置优化**：
- **文中 CTA**：放在"代码示例"小节之后、"常见错误"小节之前（用户刚学会怎么写，正处于"想试试"的状态）
- **文末 CTA**：放在 FAQ 之前（FAQ 之后用户通常直接关页面）

### 流程 4：注册/登录

**超限弹窗出现时机评估**：

当前设计：用户点 Convert → 检测超限 → 弹窗。问题是用户已经粘贴了内容、等着下载时被打断，会感到被"钓鱼"。

**优化方案（内联提示 + 弹窗双保险）**：
1. 转换按钮旁始终显示剩余用量（当前已有此设计）
2. 当剩余用量为 0 时，转换按钮变为 "Sign up to Convert"（按钮文案变化 + 颜色变灰），在按钮区域内联展示注册引导
3. 如果用户仍点击（或第一次进入时就为 0），弹出 Modal 作为兜底

**核心原则**：让用户在投入时间之前就知道限制，而不是投入时间之后才告知。

### 流程 5：Dashboard / 转换历史

**"无法重新下载"的体验冲击**：

Dashboard 中的历史记录只能看不能用（不存储原文件）。用户看到列表自然期望能重新下载。

**缓解方案**：
1. Dashboard 中明确标注："Conversion history is for your reference only. Files are not stored on our servers for your privacy."（将限制转化为隐私卖点）
2. 每条记录不要有任何看起来像"下载"的按钮/链接
3. 长期考虑：Dashboard 是否真的需要独立页面——如果只是"今日剩余用量"，Header 里一个小气泡即可

## 3. 潜在体验问题清单

### P0 — 直接导致用户流失

**问题 1：移动端 CodeMirror 粘贴兼容性**
- **描述**：CodeMirror 6 在移动端浏览器（iOS Safari、部分 Android WebView）中的粘贴行为可能异常——粘贴后光标错位、内容被吞、长按菜单不弹出
- **影响用户**：所有移动端用户（可能占流量 30-50%）
- **场景**：手机上从 ChatGPT 复制 Markdown 后粘贴到编辑器
- **建议**：开发阶段必须在 iOS Safari / Chrome Android / Samsung Browser 三端测试；提供 textarea fallback（渐进增强：先显示 textarea，CodeMirror 加载完成后替换）

**问题 2：非英语内容 PDF 字体缺失**
- **描述**：Puppeteer 在 Render 服务器上渲染 PDF 时，中文/日文/韩文等非拉丁字符可能因缺少字体而显示为方块（tofu）
- **影响用户**：所有非英语内容用户（海外华人、日韩用户、多语言文档用户）
- **场景**：粘贴包含中文的 AI 输出并转换为 PDF
- **建议**：Render 服务器必须安装 Noto Sans CJK 等多语言字体；或在 Puppeteer 渲染时注入 Google Fonts web font CSS。**技术架构文档必须明确此方案**

**问题 3：格式切换器导航导致编辑器内容闪失**
- **描述**：格式切换器是 `<a>` 导航链接，点击后页面跳转。即使 sessionStorage 保存了内容，在网络较慢时用户会经历"内容消失 → 白屏 → 内容恢复"
- **影响用户**：所有切换格式的用户
- **场景**：粘贴很长的内容后想从 PDF 切到 Word
- **建议**：使用 Next.js `<Link>` 客户端导航（不做完整页面刷新）；切换时先保存 sessionStorage 并显示骨架屏，目标页恢复后隐藏。**绝对不能出现内容消失再出现的视觉跳动**

### P1 — 显著影响体验

**问题 4：超长内容（10万字+）性能**
- **描述**：CodeMirror 6 渲染超长内容可能卡顿；实时预览解析变慢；PDF 生成可能超时
- **影响用户**：粘贴长内容的用户
- **建议**：(a) 实时预览做 debounce（输入停止 300ms 后再渲染）；(b) 超长内容显示预警；(c) 设置内容上限（如 500KB）并给出友好提示

**问题 5：非技术用户不知道"粘贴到哪里"**
- **描述**：CodeMirror 的行号、语法高亮可能让非技术用户觉得这是"程序员工具"
- **影响用户**：首次访问的非技术用户（最大群体）
- **建议**：已通过引导型示例 + sub-heading + placeholder 文案方案解决（见第 1.2 节）。另建议首次访问时在编辑器上方显示一行 3 步引导条："1. Paste your text → 2. Preview → 3. Download PDF"

**问题 6：同时转 PDF 和 Word 需切换页面**
- **描述**：转完 PDF 想再转 Word，需要点格式切换器到 Word 页 → sessionStorage 恢复 → 再点转换，且消耗两次用量
- **影响用户**：需要多格式输出的用户
- **建议**：(a) V1.0 可在转换成功反馈中加 "Also download as Word / HTML" 快捷链接（低成本）；(b) 后续版本可将转换按钮改为下拉菜单

**问题 7：转换成功后想修改再转**
- **描述**：下载 PDF 后发现内容要改，回到网站（页面没刷新）编辑器内容还在，改完再转可能被告知超限
- **影响用户**：需要修改后重新转换的用户
- **建议**：(a) 转换成功反馈中提示 "Downloaded! You have X conversions remaining today."；(b) 转换成功后不清空编辑器内容

### P2 — 体验不够好但不阻塞

**问题 8：Word 生成质量与用户期望落差**
- **描述**：docx 包对复杂格式（嵌套列表、复杂表格、代码块高亮）支持有限
- **建议**：不支持的格式优雅降级（纯文本）而非崩溃（乱码）；只有真实客服/GSC 证据表明用户普遍困惑时，再评估在指南或帮助文档中说明，不回填工具页长文

**问题 9：Copy HTML 功能的用户认知**
- **描述**：非技术用户不理解 "Copy HTML" 是什么
- **建议**：按钮文案改为 "Copy HTML Source Code"，增加 tooltip "Use this to paste into a website or email editor."

**问题 10：迷你编辑器在移动端可用性差**
- **描述**：200px 高度在移动端上下排列后每个区域只有约 100px，几乎不可用
- **建议**：移动端改为"展开/收起"模式，默认只显示预渲染示例 + "Try it yourself" 按钮，点击后展开为近全屏编辑器

**问题 11：匿名用户清除 localStorage 后用量重置**
- **描述**：通过无痕模式/清缓存可绕过限制
- **建议**：V1.0 接受此现实，IP 限制作为主要防线，localStorage 辅助。不要为防滥用增加复杂度

**问题 12：PDF 分页位置不合理**
- **描述**：Puppeteer 自动分页可能在表格/代码块/标题中间断开
- **建议**：CSS 分页控制：`h1,h2,h3 { page-break-after: avoid; }` `table, pre { page-break-inside: avoid; }`，成本极低效果显著

## 5. 页面信息结构优化建议

### 5.1 工具页首屏信息层级

当前产品结构文档的布局缺少 H1 位置。建议调整后的信息层级：

```
Header (Logo + Nav)
    │
    ▼
H1: Convert Markdown (.md) to PDF — Free Online Tool （SEO 用）
Sub-heading: Convert your Markdown or AI-generated text into a professional PDF in seconds.（用户用）
    │
    ▼
格式切换器 [PDF] [Word] [HTML]
    │
    ▼
编辑器(左 "Markdown Input") + 预览(右 "Live Preview")
    │
    ▼
操作栏（Upload + Convert + 用量信息）—— 桌面端始终可见
    │
    ▼
全站 Footer
```

### 5.2 格式切换器设计

- **视觉权重适中**：类似 Google Translate 语言切换器——扁平、紧凑、当前选中项有明显但不突兀的高亮
- **不应太高**：避免分散对编辑器的注意力
- **不应太低**：用户需要知道"不只能转 PDF"

### 5.3 工具完成后的页面收束

- 工具栏结束后直接进入全站 Footer，不再插入 How-to、Why、Features、FAQ、指南推荐或“了解更多”链接行
- Footer 保留工具、指南、法律和语言入口，承担站点级导航，不侵入转换任务
- 若未来增加任何主体内容，必须先有真实用户/GSC 证据，并证明该内容不能由现有指南承接

### 5.4 移动端信息密度

- 格式切换器 + 编辑/预览 Tab 两层控件会让顶部拥挤。考虑将编辑/预览切换改为侧滑（左滑看预览，右滑回编辑）
- 底部操作栏 Convert 按钮占至少 60% 宽度，Upload 缩小为图标按钮
- 底部固定操作栏不能遮挡编辑器底部的输入内容

## 6. 需要重点关注的高风险体验点

按风险程度排序：

### 风险 1：首次访问 3 秒内用户是否理解"该做什么"

**风险**：非技术用户面对 CodeMirror 编辑器可能觉得这是"程序员工具"而直接关闭。

**缓解**：H1 + 一句格式专属说明确认“来对地方了” → 空编辑器 placeholder 明确输入位置 → 粘贴后预览区立即给出格式化反馈。不再增加预填、三步引导条、徽章或帮助模块。

### 风险 2：移动端粘贴和编辑体验

**风险**：移动端粘贴不顺畅 = 整个使用路径崩溃。ChatGPT 移动端用户量巨大，这不是边缘场景。

**缓解**：textarea fallback + 渐进增强策略（先 textarea，CodeMirror 加载完成后替换）。必须在 iOS Safari / Chrome Android / Samsung Browser 三端测试。

### 风险 3：PDF 生成速度和成功率

**风险**：Render $7/月机器跑 Puppeteer 在高并发时可能超时。用户等 10 秒没反应就走了。

**缓解**：转换按钮点击后立即显示进度反馈（"Generating your PDF..." 配动画）；30 秒超时后友好提示；考虑展示等待页面而非仅 loading spinner。

### 风险 4：格式切换时的内容丢失感

**风险**：哪怕 0.5 秒白屏，用户也会恐慌"内容是不是没了"。

**缓解**：Next.js Link 客户端导航 + 骨架屏过渡，实现视觉上的"无缝切换"。

### 风险 5：Word 转换质量

**风险**：/to-word/ 是 SEO 突破口（KD 12），第一批获得流量。如果 Word 输出质量差，第一印象毁了。

**缓解**：开发阶段用 20+ 种不同 Markdown 测试 Word 输出；不支持的格式优雅降级（纯文本）而非崩溃（乱码）；转换结果中告知 "Some advanced formatting may appear simplified."

## 8. 2026-10-04 已实施交互修复

1. 空白输入禁用导出/复制；复制也显示loading并阻止重复点击。错误与上传反馈按当前语言展示。重试真正再次执行，编辑/上传/清空或换格式后不重试旧内容；旧成功提示定时器不覆盖新操作。
2. 读取错误保留原内容；.MD等大写扩展名可用，BOM和编码处理在浏览器完成。连续上传只应用最后一次结果；手动输入/清空/离开页面使旧读取失效。
3. 手机HTML页idle状态原本已存在按钮文字越界，390px截图与宽度测量确认；现采用分行和不换行按钮，反馈单行独占区域并可换行，保留底部安全区。
4. 左右统计口径分别为源码和正文；源码包含格式/空白，正文排除空白和链接地址，包含代码及表格文字。预览截断时明确是片段统计，错误时保留旧结果并提示。
5. 内容在同标签页共享内存中即时保持，保存防抖300ms；导航/pagehide/隐藏标签页前立即保存。存储失败不丢内存草稿，但不承诺整页刷新后的恢复；无法保存的跨语言/root导航被拦截并提示。
6. 复制仍为HTML源码。支持ClipboardItem的浏览器在点击时立即发起text/plain写入，把异步渲染Promise作为数据，保留Safari的用户激活；其他浏览器降级writeText。
7. Word输出保持支持的Markdown内容顺序，嵌套缩进和任务状态可见；预览副标题改为“Markdown效果预览”，不承诺Word/PDF分页与网页完全一致。
