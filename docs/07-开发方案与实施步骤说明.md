## 1. 开发总体思路

### 1.1 核心原则

**风险前置、依赖驱动、串行为主并行为辅。**

本项目有一个明确的技术风险——Puppeteer 在低内存服务器（Render Starter 512MB）上的稳定性。如果 PDF 生成不可靠，整个产品的核心价值归零。因此：

1. **最高优先级验证后端 PDF/Word 生成能力**，在写任何前端页面之前确认后端可行
2. **从底层往上搭建**：基础设施 → 后端 API → 前端核心 → 用户系统 → SEO/内容 → 上线
3. **每个阶段有明确的交付物和检查点**，通过检查点才进入下一阶段
4. **不做并行美化**：Frank 是兼职开发（主业央企管理岗），同时推进多条线会导致上下文切换损耗。除非两个任务明显无依赖，否则串行执行

### 1.2 不重新设计需求

本文档的职责是**把已定稿的 7 份文稿转化为可执行步骤**，不引入新功能、不修改已确认的技术选型、不偏离 01 主线文档第 7 节的"非目标"清单。所有开发任务均可溯源到具体文稿的具体章节。

### 1.3 阶段划分依据

| 划分维度 | 说明 |
|---------|------|
| **依赖关系** | 后续工作依赖前置工作的产出（如前端转换功能依赖后端 API） |
| **风险等级** | 高风险项尽早验证，失败时有充足时间调整方案（如切换 Render 实例规格） |
| **功能完整性** | 每个阶段结束时应达到一个"可体验"的里程碑，而非散落的半成品 |
| **开发效率** | 同类工作集中处理（如所有 SEO 相关任务放在同一阶段），减少心智切换 |

## 3. 各阶段开发目标

### Phase 0：项目脚手架
**目标**：从零搭建 Monorepo 项目骨架，前后端均可本地启动，数据库 Schema 就绪。

### Phase 1：高风险验证
**目标**：验证后端技术选型的可行性——Puppeteer 在 Render 上能否稳定生成 PDF，docx 包能否生成质量合格的 Word 文件。**这是整个项目的"生死关"。**

### Phase 2：前端核心
**目标**：实现产品的核心价值——用户打开网站、粘贴 Markdown、预览、一键转换下载。三种格式（PDF/Word/HTML）端到端可用。

### Phase 3：用户系统
**目标**：实现完整的用户认证和用量管控闭环——注册/登录、用量追踪、超限提示、转换历史。

### Phase 4：SEO + 内容 + i18n
**目标**：实现所有 SEO 基础设施和内容页面——i18n 双语路由、TDK/JSON-LD/sitemap 等技术 SEO、3 篇指南页、工具页 SEO 内容区、辅助页面。

### Phase 5：打磨 + 测试 + 上线
**目标**：质量打磨、跨端测试、性能优化，最终部署上线并提交搜索引擎收录。

### 5.2 关键依赖链

| 依赖链 | 说明 |
|--------|------|
| 后端 API → 前端转换 | 前端 PDF/Word 转换按钮必须有后端 API 可调 |
| 编辑器 → 转换流程 | 转换功能从编辑器获取 Markdown 内容 |
| Auth → 用量控制 | 登录用户用量通过 DB 追踪，需要 Auth Session |
| 用量控制 → 转换流程 | 转换前必须检查用量，转换后必须写入 DB |
| 转换流程 → Dashboard | 转换历史写入 DB 后 Dashboard 才有数据展示 |
| 页面存在 → SEO | generateMetadata / JSON-LD 需要页面先存在 |
| i18n 架构 → 所有页面 | 路由分组 `[lang]/` 是所有页面的前提 |

### 5.3 反向依赖（注意不要打破）

| 被依赖方 | 依赖方 | 打破后果 |
|---------|--------|---------|
| sessionStorage key (`md-editor-content`) | 编辑器、格式切换器、MiniEditor CTA | 内容丢失 |
| localStorage key (`md-usage-{date}`) | 匿名用量追踪、超限提示 | 用量判断失效 |
| Supabase daily_usage UPSERT SQL | 用量递增逻辑 | 限额绕过 |
| 后端 API 响应格式 | 前端 API Client | 转换功能崩溃 |

## 11. 开发过程中需要重点防止遗漏的事项

以下事项散布在多份文稿中，容易在开发中遗漏。**每完成一个相关功能时，请回到此清单逐条核对。**

### 11.1 数据流正确性（来源：06-数据库设计 §5）

| # | 事项 | 错误后果 | 涉及文件 |
|---|------|---------|---------|
| D1 | 转换成功后写入顺序：先 UPSERT daily_usage，再 INSERT conversion_history | 颠倒可能导致扣量但无记录 | `hooks/use-conversion.ts` |
| D2 | 转换失败时：不写 daily_usage，写 conversion_history(status='failed') | 失败扣量 = 用户投诉 | `hooks/use-conversion.ts` |
| D3 | HTML 转换：写 conversion_history(format='html')，不写 daily_usage | HTML 被误扣量 | `hooks/use-conversion.ts` |
| D4 | 匿名用户转换：数据库零参与，仅 localStorage + IP 限流 | 匿名用户数据入库 = 设计违规 | `lib/rate-limit/` |

### 11.2 SEO 红线（来源：02-SEO策略 §3.3 + §5）

| # | 事项 | 错误后果 |
|---|------|---------|
| S1 | 所有 Title 必须包含 "Markdown (.md)"，不能只写 "MD" | Google 误判为 Maryland/Medical Doctor |
| S2 | 正文中 "Markdown" 全称出现频率远高于 "md" 缩写 | 同上 |
| S3 | 每页设置 canonical URL | 重复内容惩罚 |
| S4 | 英文和中文页面互设 hreflang，x-default 指向英文 | 多语言 SEO 失效 |
| S5 | auth/login 和 dashboard 设 noindex | 无用页面占用 crawl budget |
| S6 | 工具页 SEO 内容区至少包含 How-to + Why + Features + FAQ(5+) | SEO 内容不足 |

### 11.3 交互体验红线（来源：03-1-交互补充 §3 + §6）

| # | 事项 | 错误后果 |
|---|------|---------|
| U1 | 格式切换**绝对不能**出现内容消失再出现的视觉跳动 | 用户恐慌"内容没了" |
| U2 | 转换按钮在桌面端始终可见（fixed/sticky 定位） | 长内容时按钮滚出视窗 |
| U3 | Dashboard 不显示任何类似"下载"的按钮 | 用户期望重下载但不可能（不存文件） |
| U4 | 超限提示应在用户投入时间之前出现（转换按钮旁显示剩余次数），而非投入后弹窗 | 被"钓鱼"感 |
| U5 | PDF 分页 CSS：h1-h6 page-break-after: avoid，table/pre/blockquote page-break-inside: avoid | 表格/代码块中间断页 |

### 11.4 技术细节（来源：05-技术方案 散布各节）

| # | 事项 | 说明 |
|---|------|------|
| T1 | CodeMirror 6 必须 dynamic import | 阻塞首屏 = Lighthouse 扣分 |
| T2 | 实时预览 debounce 300ms | 无 debounce = 超长内容卡顿 |
| T3 | sessionStorage key 统一为 `md-editor-content` | 多处读写必须用同一个 key |
| T4 | localStorage 匿名用量 key 为 `md-usage-{YYYY-MM-DD}` | 日期格式不一致 = 限额失效 |
| T5 | Puppeteer 启动参数包含 `--disable-dev-shm-usage --no-sandbox --single-process` | 缺少 = Render 上 OOM |
| T6 | 后端 CORS 仅允许 `ALLOWED_ORIGIN` 环境变量指定的域名 | 开放 CORS = 安全漏洞 |
| T7 | 文件名生成：H1 提取 → 特殊字符去除 → 空格转连字符 → 限 50 字符 | 文件名乱码/过长 |
